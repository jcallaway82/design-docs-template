1. Overview

This document specifies the data schema for CLAWE UI — a standalone application (its own process, own executable, own database) with a maintenance mode for authoring radars/modes/waveforms and an operate mode for runtime control, which STS UI drives over a TCP network connection (interface B) to play a closed-loop CLAWE radar inside a static scenario. CLAWE UI is not a PRISM plugin — it is architecturally independent of STS, though it is built to look, feel, and be organized like it. This document covers only CLAWE UI's own data — not the STS-side "Add Emitter to Static Scenario" integration or the interface B message contract, which are out of scope here.

The schema below is built from the ClaweRadarInstance / ClaweRadarModeInstance / ClaweWaveformInstance structures defined in the CLAWE UI Requirements.pptx deck (slides 5–13, 27–32), cross-referenced against the existing legacy CLAWE implementation in sparta/Components/libSPARTABase/.../SMDLObjects/CLAWE/, and designed to persist as its own SQLite database (CLAWE DB). Where this document references STS's PRISM.Database project, it is strictly as a design-pattern reference — matching conventions for consistency and familiarity — not a shared codebase, shared connection, or shared schema. See §3 for exactly what is and isn't shared.

Approved: this schema was reviewed and approved as-is at the 2026-08-18 design meeting. Subsequent changes: AlternateName narrowed to one NATO + one ELNOT per radar to match STS (v2.1; confirmed by the lead), Modes narrowed to require at least one mode per radar (v2.2; confirmed directly by the lead), and v3.0 folds in the changes the CLAWE Waveform Calculations.pptx deck requires — the Phase modifier splits into Full / Partial Phase Encoded, NumPulses is added as distinct from FFT size, and BaseWaveform gains a CW value — see the Changelog. CLAWE DB and PrismDB are completely separate, independent databases — CLAWE UI gets its own ClaweDbContext and its own SQLite file, not entities registered into STS's shared PrismDbContext.
Related documents: this document covers CLAWE UI's own persisted data model. The Interface B design covers the STS UI ↔ CLAWE UI network contract, including the derived ClaweRadarSummary projection (§4.5). The waveform-calculation formulas the summary screen and waveform browser depend on are specified in CLAWE Waveform Calculations.pptx (a tracked spec doc is planned).

The v2.x reserved placeholder on PhaseEncoded is the wire-compatible hook this split uses.

3. Two-Layer Storage Rationale

Decided: CLAWE DB and STS's PrismDB are completely separate, independent databases running in two independent applications. CLAWE UI gets its own ClaweDbContext and its own SQLite file (e.g. clawe.db) in its own process — not a set of entities registered into STS's PrismDbContext alongside Emitter/ TestSuite/etc. The rest of this section borrows PRISM.Database's conventions for consistency and familiarity, but nothing is shared at runtime: no shared connection, no shared SchemaVersion table, no shared PK sequence, no shared process.

STS's PRISM.Database establishes a two-layer pattern for its Emitter schema that CLAWE UI's own database borrows as a design reference: a canonical protobuf blob holding the full nested object graph (EmitterProtoBlob), plus a family of flat, EF-mapped "rollup" tables (EmitterModeRollup, EmitterModeBehaviorRollup, EmitterModeModulationRollup) that exist purely to serve range/flag filtering across a shared library tuned for 1–2 million emitter rows.

Why this schema is thinner: EmitterMaker filters a large, largely read-only shared library it doesn't author — the rollup tables exist to answer "find emitters where PRI is between X and Y" without deserializing a blob per row. The CLAWE Emitters App is its own authoring tool: the database is the save file for a UI directly editing radars, modes, and waveforms it owns. There is no bulk-import pipeline and no requirement in the deck for range/threshold filtering across a radar library — the only listed UI need is a picker list (radar/mode/waveform name and type). Building a full rollup layer for all nine modifier shapes now, with no filter query to validate the design against, risks getting it wrong and redoing it later. The blob stays canonical either way, so adding rollup tables later is additive — a new schema-update step walks the existing blobs and populates new tables — not a rework of what's already there.

Kept from the established pattern (conventions only — nothing is actually shared at runtime, per the independent-database decision above): a single protobuf blob per radar as the canonical, full-fidelity, round-trippable source of truth (ClaweRadarProtoBlob, 1:1 shared-PK child of ClaweRadar, mirroring EmitterProtoBlob); long surrogate autoincrement primary keys named <Entity>Pk; plain C# enums stored as native SQLite integers; no EF Core Migrations project — schema built procedurally in ClaweDbContext.OnModelCreating and evolved via ClaweDB's own versioned ApplySchemaUpdatesAsync()-style patch list and its own SchemaVersion table.

Diverged from the established pattern: STSSE emitters carry a separate 26-char ULID string as their public-facing identity, decoupled from the surrogate PK. For CLAWE UI we decided the already-required-unique Name is sufficient as the sole external handle — no separate public ID field is modeled.

Thinned from the established pattern: one summary row per radar / mode / waveform (id, name, type only — enough for picker and dropdown UI, e.g. an Auto-mode schedule's WaveformID selector) instead of a rollup table per queryable dimension. No behavior/modulation rollup equivalent is proposed for the modifier stack.

3.1 Worked example — how a mode links back to its radar

Slide 5 states the cardinality directly: "Radar includes 0 to many radar modes." That one-to-many relationship is represented twice, once per storage layer, and the two representations look different on purpose:

Narrowed to 1..N (v2.2, Sep 2026): confirmed directly with the lead that there is no use case for a radar with zero modes — matching STS, which effectively requires >=1 mode per emitter too. The deck's own "0 to many" wording above is left as a direct quote of slide 5; CLAWE's schema itself now requires at least one.
Two representations, one relationship: in the canonical blob, a mode has no identity outside its parent — it's just an element of the modes list inside that radar's ClaweRadarInstance message. In the thin SQLite index, a mode is its own row, so it needs an explicit foreign key back to the radar row it belongs to. Same relationship, expressed as containment in one layer and as a key reference in the other.

Concretely, for a radar with two modes:

TableExample rows
ClaweRadar ClaweRadarPk = 1, Name = "AN/APQ-Demo", ModeCount = 2
ClaweRadarMode ClaweRadarModePk = 101, ClaweRadarPk = 1, Name = "TTR Search"
ClaweRadarModePk = 102, ClaweRadarPk = 1, Name = "TTR Track"

Both mode rows carry ClaweRadarPk = 1 — that's the entire linkage. It's the same pattern EmitterModeRollup.EmitterPk uses in the existing PRISM.Database schema (Fig. 2's ClaweRadar ||--|{ ClaweRadarMode line is exactly this: "one radar has one-or-more modes, each mode row points back to exactly one radar").

Meanwhile, inside ClaweRadarProtoBlob.ProtoBytes for ClaweRadarPk = 1, the same two modes exist only as the two entries of one repeated ClaweRadarModeInstance modes field on the single ClaweRadarInstance message — there's no ClaweRadarPk column to point anywhere, because both modes are physically inside that one radar's serialized bytes. If you deleted the ClaweRadar row, the cascade delete removes the ClaweRadarMode rows and the one blob row that contains both modes' full data — nothing can be "orphaned" at the blob layer the way a dangling foreign key could at the SQLite layer.

This is also why ClaweRadarMode.Name is only required to be unique per radar (via the composite index on (ClaweRadarPk, Name), not Name alone) — two different radars are free to both have a mode named "Search", because uniqueness is scoped to the parent, exactly like the deck's own wording ("unique within a radar").

4.5 Derived projections (not stored)

Two projections are computed from the canonical model and never persisted as their own entities:

ProjectionConsumed byDerivation
ClaweRadarSummary Interface B — RequestRadars() response A flattened, rolled-up view of a radar and its modes for STS's Add-Emitter picker — radar/mode identity plus per-mode WaveformType[] {Pulsed, Single Pulse, CW}, MinFreq/MaxFreq, MinPRI/MaxPRI, MinPW/MaxPW, and ModulationType[] (a 6-value subset of the modifier categories). Deliberately carries no ClaweWaveformInstance detail. Field list and rollup rules: Interface B design §5.
Waveform calc rollup Waveform Summary Screen; Waveform browser filters Scalar metrics per waveform (CPI duration, processing gain, eclipsing fraction, range/velocity ambiguity zone size + count) plus min/max freq/PRI/PW and modulation-type flags, computed by the CLAWE.Calc engine from the waveform + its mode's envelope + fixed scenario assumptions. Cached in a ClaweWaveformCalcRollup table (added by an additive schema-update that walks existing blobs — the blob format is unchanged), so the browser filters thousands of waveforms without deserializing a blob per row. Formulas: CLAWE Waveform Calculations.pptx.
Why these are not in the blob: both are functions of data already in the canonical model (plus, for the calc rollup, a set of fixed scenario assumptions that live in code, not the schema). Storing them would create a second source of truth to keep in sync on every edit. They are recomputed on write and cached only where a query needs them — the same "rollup tables are additive" reasoning in §3.
