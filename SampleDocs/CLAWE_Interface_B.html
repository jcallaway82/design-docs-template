1. Overview

Interface B connects STS UI to CLAWE UI so that a user building a static scenario in STS can add a live, closed-loop CLAWE radar to it. In STS Settings the user registers an interactive-emitter source (a name + the CLAWE endpoint); in a static scenario the user clicks "Add Emitter", picks that source, and STS fetches CLAWE's live list of radars and modes to populate the picker. STS can also remote-launch CLAWE UI's maintenance mode so the user can edit a radar without leaving the workflow.

The cast:

  • STS UI — the existing PRISM/STS application. The client on this interface.
  • CLAWE Proxy — an always-on CLAWE-side process that owns the interface-B (and interface-C) network connection and launches views on request. STS connects here, never to a view directly.
  • Maintenance View — a single-purpose CLAWE UI window for authoring radars, modes, and waveforms. Singleton: one instance at a time, and the only writer to CLAWE DB.
  • Execution View — a single-purpose CLAWE UI window locked to one assigned radar mode, launched by HOCA over interface C to run a scenario. 0..n may run at once. Not launched over interface B, but listed here for context.
  • CLAWE DB — CLAWE UI's own SQLite database. One per CLAWE host.
  • RabbitMQ broker — the message broker all three TCP interfaces (A, B, C) run over.
Why a proxy, not the view: STS/CLAWE/HOCA may run on different machines, and CLAWE's views are single-purpose and short-lived (a maintenance view is only up while someone is editing; an execution view only while a scenario runs). A persistent proxy gives STS and HOCA a stable endpoint regardless of which views happen to be open, and is the natural place to enforce "one maintenance view at a time" and to answer RequestRadars() from a read-only DB connection without a view running at all.

2. Transport & Topology

Transport stack

LayerChoice
NetworkTCP. STS UI, CLAWE, and HOCA may be co-located or on separate machines — nothing may assume same-host access to another component's database or filesystem.
MessagingRabbitMQ (AMQP 0-9-1). Same broker family as interfaces A and C, so STS carries one messaging stack for all of them. CLAWE references the official RabbitMQ.Client.
SerializationProtobuf. Messages defined in proto/clawe/v1/clawe_interface_b.proto, compiled in CLAWE.Proto; CLAWE.Contracts holds the summary builder and the names/versions below, and CLAWE.Messaging the RabbitMQ transport.
Message classesrequest-response (RPC), command (fire-and-ack), pub-sub (fanout events).
Divergence from the reference implementation: STS's existing STS↔HOCA channel (PRISM.Host/Services/HocaLiteService.cs) is TCP/JSON + NetMQ (ZeroMQ) + Protobuf, not RabbitMQ. The interface deck specifies RabbitMQ for all three interfaces, and the project follows the deck (OQ-2, resolved in iteration 4), so STS's side of interface B needs a RabbitMQ client too. The message types and CLAWE.Contracts stay transport-neutral; only CLAWE.Messaging references a broker client.

2.1 Broker objects

ObjectTypePurpose
clawe.ifaceB.rpc.<source>queueSTS → CLAWE Proxy. Carries RequestRadars (request-response, via reply_to + correlation_id) and LaunchMaintenanceUiCommand (command, ack only). One per CLAWE endpoint, namespaced by the source name STS registered (the proxy's SourceName setting), so several CLAWE hosts can share one broker (OQ-11 — the STS side must agree the naming). The queue is durable (RabbitMQ 4 refuses non-durable, non-exclusive queues), and requests expire after 30 s, so a command queued while the proxy was down can't open an editor much later.
clawe.ifaceB.eventsfanout exchangeCLAWE → STS. Carries RadarModifiedEvent. STS binds a transient queue on connect; any number of STS instances may subscribe.

Every message travels inside an InterfaceBEnvelope (a protobuf oneof) so the receiver dispatches on payload type and metadata (timestamp, protocol version) rides alongside — the same pattern STS uses for its own CoreEnvelope / ScriptEnvelope.

RuleDetail
Proxy lifetime The proxy starts at user logon and stays up — a headless process in the user's session, not a Windows Service, so it can open views on the user's desktop (Design DD-21). It owns the RabbitMQ connection for interfaces B and C, and holds a read-only connection to CLAWE DB for answering RequestRadars(). It is the only broker client on the host: views talk to it over local named pipes (Design DD-20).
Maintenance = singleton Exactly one maintenance view per host at a time. Enforced by a system-wide named mutex (Global\CLAWE_UI_Maintenance) that the view takes on startup, before touching the database. A second launch asks the running view to come forward (over the clawe-maintenance pipe) and exits. The proxy doesn't probe the mutex: it knows a view is running from its registration, and asks it to come forward the same way.
Maintenance = sole writer Only the maintenance view writes CLAWE DB. The proxy and execution views open it read-only (Mode=ReadOnly). A DB write-owner row backs the mutex for defence in depth: the view claims it at startup and every commit checks it first, on top of SQLite WAL + busy_timeout.
Execution = 0..n Any number of execution views may run at once; each is locked to one assigned radar mode and does not write the DB. Launched over interface C, not B.
Two launch paths A view can be started by the proxy (in response to a network message) or directly by a batch file / double-click. Both honour the singleton mutex. Every view registers with the proxy (over the clawe-proxy pipe), however it was launched, so subsequent LaunchMaintenanceUI() calls focus it. The maintenance view works with no proxy running; it keeps trying to register in the background.
Multi-host Each CLAWE host runs its own proxy and its own CLAWE DB. The singleton rule is per host — cross-host coordination is not attempted (different hosts have different databases). Host identity / discovery is an open item (OQ-11).
Behaviour on a second LaunchMaintenanceUI() — proposed, pending the lead (OQ-10): the proxy focuses the running view, opening the requested radar, and returns FOCUSED — what FR-44 already says, and what iteration 4 built. The cross-host case can't arise: each host has its own proxy and its own database. REJECTED means the view couldn't be started or didn't respond (B302). One Windows limit: a background process can't take the foreground, so a focus STS asks for may only flash the view's taskbar button.

4. Message Catalog

4.1 RequestRadars — request-response

STS → CLAWE Proxy. Asks for the current radar list to populate the Add-Emitter picker.

FieldTypeCard.Description
RequestRadars — no fields. The request itself is the signal.

Response — RequestRadarsResponse:

FieldTypeCard.Description
radarsClaweRadarSummary0..NEvery radar in CLAWE DB, each with its modes rolled up. See §5.
source_namestring1Echoes the interactive-emitter source name STS registered for this CLAWE endpoint, so STS can attribute the list.
schema_versionstring1The ClaweRadarSummary contract version (e.g. clawe-ifaceB-1), so STS can detect a mismatch.
errorstring0..1Set when CLAWE couldn't read its database (FM-5, B202): radars is then empty and this says why, so STS shows the source as errored rather than offline. Added in v0.3 of this document (iteration 4).
Why no waveform detail: STS only needs enough to let the user pick a radar mode and then enter a valid center frequency (checked against the mode's CF constraints). PRI and PW are not settable from STS, so waveform-instance detail — hundreds to thousands of entries per mode — is deliberately excluded. The response is a rollup, not a dump of ClaweRadarInstance.

4.2 LaunchMaintenanceUiCommand — command

STS → CLAWE Proxy. Fire-and-ack; STS gets a result but no view handle.

FieldTypeCard.Description
radar_namestring0..1Optional. If set, the maintenance view opens with this radar selected.

Ack — LaunchMaintenanceUiResult:

FieldTypeCard.Description
outcomeenum1LAUNCHED (a new maintenance view was started and registered), FOCUSED (one was already running and was asked to come forward), or REJECTED (a view couldn't be started, didn't register in time, or didn't respond — B302; see OQ-10).
messagestring0..1Human-readable detail: why, on REJECTED; or e.g. "No radar named 'X'." on FOCUSED when the requested radar doesn't exist.

4.3 RadarModifiedEvent — pub-sub

CLAWE → STS, via the clawe.ifaceB.events fanout exchange. Published whenever a radar, mode, or waveform write commits, so STS can call RequestRadars() once and then refresh only on change instead of polling.

FieldTypeCard.Description
radar_namestring1The affected radar. On rename, this is the new name; previous_name carries the old one.
previous_namestring0..1Set only when change_kind = RENAMED.
change_kindenum1CREATED, UPDATED, RENAMED, DELETED. UPDATED covers any change to the radar's modes or waveforms too — the event is radar-grained, not field-grained.
timestampTimestamp1Commit time (UTC).
source_namestring1As in the RequestRadars response.
Coalescing: a burst of edits (e.g. saving a radar with many modes) should not produce a storm of events. The publisher should debounce per radar — one UPDATED after the last write in a short window — with CREATED/DELETED/RENAMED still sent promptly.

5. ClaweRadarSummary Reference

A flattened, rolled-up projection of a radar and its modes — derived from the canonical ClaweRadarInstance (see the Data Schema §4.5), never stored. Until the calc-rollup layer exists, the proxy builds it by walking each radar's protobuf blob; afterwards it is assembled from cached rollup rows without deserializing a blob.

Iteration 4 is envelope-only. The frequency, PRI and PW bounds below come from the mode's constraint envelope. A ClaweWaveformInstance stores its own fixed centre frequency, PRI and PW (FR-64), but each must lie inside that envelope, so they cannot widen it. Reporting the span of the waveforms actually authored instead would come with iteration 10's rollups (to confirm with the lead). The waveform-derived fields available today — waveform_types and modulation_types — are already included. Built by CLAWE.Contracts' RadarSummaryBuilder; a 1,000-radar catalogue takes about 37 ms (OQ-12).

5.1 Radar level

FieldTypeCard.Derived from
namestring1ClaweRadarInstance.name. Unique within the database.
descriptionstring0..1ClaweRadarInstance.description.
alternate_namesAlternateName{type, value}0..2The radar's NATO name and/or ELNOT. "UI should mirror STS UI for these fields."
modesClaweRadarModeSummary1..NOne per mode. §5.2.
Cardinality note: the interface deck writes AlternateName as "0 to many," but also says the UI mirrors STS, which allows exactly one NATO name and one ELNOT. CLAWE's own schema (v2.1) narrows this to 0..1 per kind, which the lead confirmed on 2026-09-09. This document follows the schema.

5.2 Mode level — ClaweRadarModeSummary

FieldTypeCard.Derived from
namestring1ClaweRadarModeInstance.name. Unique within the radar.
descriptionstring0..1ClaweRadarModeInstance.description.
radar_mode_typeenum {Search, TAR, TTR, Missile}1ClaweRadarModeInstance.radar_mode_type. TTR only for v1.
operating_modeenum {Manual, Auto, Cognitive}1Which operating_mode oneof branch is set.
waveform_typesInterfaceBWaveformType {Pulsed, SinglePulse, CW}1..NDistinct set of the mode's authored waveform base types, unioned with the base types the mode's constraint envelope allows (pd_constraints present → Pulsed; sp_constraints present → SinglePulse). CW: not produced yet (OQ-7).
min_freq_hz / max_freq_hzdouble1From the mode CF envelope — range → endpoints; discretes → min/max of the list — widened by any per-waveform center-frequency rollup that falls outside it.
min_pri_s / max_pri_sdouble0..1Min/max over the mode's PD waveform PRI rollups, unioned with pd_constraints.pri range. Absent when the mode allows no PD waveforms.
min_pw_s / max_pw_sdouble1Min/max over the mode's waveform PW rollups, unioned with the PD/SP pw constraint ranges. A PD duty-cycle constraint contributes duty % × the PRI bounds.
modulation_typesInterfaceBModulationType {Phase, Frequency, PRI, PW, LeadingEdge, TrailingEdge}0..NUnion of the modifier categories enabled across the mode's waveforms. A 6-value subset of the nine modifier categories — no Pulse Compression, Amplitude, or Discrimination (OQ-8).
Frequency validation is the point: STS lets the user set a scenario emitter's center frequency and checks it against "the radar mode's CF constraints." min_freq_hz / max_freq_hz (plus, for a channelized range, the channel spacing — carry it if STS needs to snap to channel centers) are what STS validates against. Everything else in the mode summary is for display and filtering in the picker.

7. Failure Matrix

Severity
Critical High Medium Low
Recovery
Abort Retry Degrade
CodeFailureSeverityRecoveryHandling
B101 Broker unreachable
STS cannot connect to RabbitMQ, or the connection drops.
 Critical Retry STS shows the CLAWE source as offline; reconnect with backoff. No radar list until restored.
B102 Proxy not running
Broker is up but nothing is consuming clawe.ifaceB.rpc; request times out.
 High Retry Same UX as B101 (source offline). The proxy is meant to auto-start; a missing proxy is a deployment fault.
B201 RequestRadars timeout
No response within the RPC deadline (large DB, slow disk).
 Medium Retry STS retries once with a longer deadline, then surfaces "couldn't load radars". Proxy should page/stream if the list is very large.
B202 CLAWE DB unavailable / corrupt
Proxy cannot open or read CLAWE DB.
 High Abort Proxy returns an error response (not a timeout) with detail. STS shows the source as errored, not merely offline.
B203 Schema/version mismatch
schema_version in the response is one STS doesn't understand.
 Medium Degrade STS parses what it can and warns; fields it doesn't recognize are ignored. Additive proto changes should not trigger this.
B204 Malformed request
Proxy receives an envelope it can't parse or an unknown payload.
 Low Abort Proxy drops it (or nacks) and logs. No response — the sender's deadline handles it.
B301 Maintenance already active
LaunchMaintenanceUI() while a maintenance view holds the mutex.
 Low Degrade Proxy asks the running view to come forward and returns FOCUSED (proposed answer to OQ-10; the cross-host case can't arise — one proxy and database per host). Never a second writer.
B302 View failed to spawn
Proxy's process launch fails (missing exe, OS refusal).
 High Abort Proxy returns REJECTED with detail; releases the mutex if it had taken it optimistically.
B401 Missed RadarModifiedEvent
STS was disconnected from the events exchange during an edit.
 Low Degrade On reconnect STS re-runs RequestRadars() unconditionally to resync. Events are an optimization, not the source of truth.

Total: 9 failure modes across connection (B1xx), request (B2xx), process (B3xx), and events (B4xx).

8. Interfaces A & C

Out of scope for this document, but for context, from STS SW Interface Descriptions.pptx:

InterfaceBetweenMessages (per the deck)
A STS UI ↔ HOCA Static-scenario control (Run, Stop, RunScenario, Pause, Resume), status updates, and RTSA real-time streams (StreamWBSpectrums, StreamNBSpectrums, StreamEDReports, StreamEDPDWs, StreamPDWs). A dedicated design doc exists for this interface; PRISM.Host/Services/HocaLiteService.cs is the current implementation.
C CLAWE UI ↔ HOCA HOCA → CLAWE: LaunchExecutionUI(ActiveRadarMode) — creates/shows an execution view for a radar mode (carries Radar Name, Mode Name, CF, Amplitude); ActivateRadar(); DeactivateRadar(). CLAWE → HOCA: LoadWaveforms(List<waveform>) — pushes all waveform instances for the active radar into HW DDR RAM; LoadSchedule(List<WaveformID, Duration>) — the Auto-mode schedule, repeated in HW. The RDI / target-report data-stream direction is not yet specified.
Why interface C launches execution mode, not interface B: maintenance is an authoring activity a scenario-builder user initiates (interface B); execution is driven by the hardware-abstraction layer as it plays a scenario (interface C). The proxy handles both, but the two view types have different lifecycles, permissions (execution never writes the DB), and cardinality (execution is 0..n).
