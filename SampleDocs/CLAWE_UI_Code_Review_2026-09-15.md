# CLAWE UI implementation review (15 September 2026)

## Scope and verdict

This is a read-only review of the current `CLAWE_UI` solution at commit `c405c09` (iteration 3 waveform editor, v0.3.0 work). I compared the Host, UI, Database, Proto, contracts, XAML, and tests with `CLAUDE.md`, `DESIGN.md`, `REQUIREMENTS.md`, the iteration timeline and review, the three referenced decks, relevant PRISM shell/editor/database patterns, and the legacy CLAWE reconciliation. This report does not treat planned iteration 4–12 features as regressions in iteration 3.

The high-level separation is sound for the authoring prototype: a standalone WPF Host, reusable theme/control project, canonical protobuf model, SQLite index tables, and tests. MVVM Toolkit observable properties and commands carry most behavior; view code-behind mainly handles WPF input/layout quirks. The main architectural debt is the persistence unit of work. One visible Save is multiple commits, and even some individual radar repository operations commit an index row before updating its canonical blob. That directly conflicts with the design's atomicity requirements and becomes more consequential when interface B starts reading the database.

## Findings, ordered by impact

### 1. High — radar index and canonical blob can diverge after a failed write

`RadarRepository.CreateRadarAsync` commits the radar row at line 64, then builds/commits the blob at lines 66 and 152–184. `UpdateRadarAsync` commits the new name/description at line 94, then rewrites the blob at line 95. `SetAlternateNameAsync` does the same at lines 142–143. Each `SaveChangesAsync` is its own transaction. If blob parsing, serialization, disk access, or the second commit fails, the index describes one state while the blob describes another, or a new radar has no blob at all. `RadarModeRepository.SaveModeAsync` refuses a radar without the canonical blob. The intended invariant is explicit in `REQUIREMENTS.md` FR-7, lines 121–128: blob and index in the same transaction. The ordinary sync tests prove successful round trips but do not inject a fault between commits. **Recommendation:** make each repository mutation a single database transaction (and for a new radar, arrange key creation and blob insertion within it), then add a rollback test at the fault boundary.

### 2. High — the combined Save has partial success and can strand a new-radar draft

`RadarListViewModel.SaveSelectedRadarAsync` lines 619–645 writes radar, mode, NATO, ELNOT, and open waveform in sequence. Its own comment at lines 581–587 acknowledges partial persistence. For a new radar, `IsCreatingNewRadar` becomes false at line 625 before the first mode save at line 626. If mode save fails, `SelectedRadar` is still null. The next Save enters neither the new-radar nor selected-radar branch (lines 620 and 628–637) and returns, while the database contains a radar that may have no mode. For an existing radar, a late failure may leave a renamed radar or changed mode despite the UI reporting “Save failed.” This is a correctness issue even if each repository operation is individually atomic. **Recommendation:** represent the footer action as one application-level transaction over the whole radar graph; refresh the UI state only after commit. Until then, preserve the draft's created primary key and report which writes committed so retry/discard is accurate.

### 3. High — switching modes clears the radar's unsaved indicator without checking radar fields

Editing `EditName`, description, NATO, or ELNOT sets `HasUnsavedChanges` through `MarkFieldEdited` (lines 241–255). A mode-pill click checks only `CurrentMode.HasPendingEdits` in `RadarEditorView.xaml.cs` line 53 and `ConfirmModeSwitchAllowed` line 283. Then `LoadSelectedModeAsync` sets `HasUnsavedChanges = false` at line 377. Reproduce: open a radar with two modes, change the radar description only, click the other mode, then close or pick another radar. The changed description remains in the form, but the discard prompt is bypassed because the flag was cleared. A direct `SelectedModeRow` assignment has the same outcome. **Recommendation:** derive the whole-editor dirty state from radar identity plus active mode/waveform state; switching a mode should preserve radar-field dirtiness and only clear the departed child draft after confirmed discard. Add a regression test for the described sequence.

### 4. Medium — schema upgrade steps are recorded after non-atomic SQL operations

`ClaweDbContext.ApplySchemaUpdatesAsync` lines 217–331 has no explicit transaction around each patch. Version 3 drops an index, deletes duplicate alternate names, and creates a new index (lines 265–286) before its version row is saved. An interruption between those statements leaves a partly upgraded file; the next launch may rerun the patch, but idempotence is not the same guarantee as rollback. Version 5 can fail while creating a uniqueness index on an older file with duplicate waveform names. `REQUIREMENTS.md` FR-10, lines 147–154, requires each step and its version record to be atomic. **Recommendation:** wrap each patch and version insert in one transaction; test a deliberate failure after the first mutation. Treat the version-3 deduplication as a data migration that needs a recoverable pre-upgrade copy.

### 5. Medium — mode identity relies on mutable, inconsistently compared names

Mode index rows have stable primary keys, but `RadarModeRepository.GetModeAsync` line 47 and waveform operations find the mode inside the blob by `Name`. `SaveModeAsync` lines 86–97 removes an old-name entry if present, then removes any entry with the new name before adding the edited mode. If blob and index drift, the latter removal silently discards that graph entry and its waveforms instead of surfacing the mismatch. The editor validates sibling names ignoring case (`RadarModeEditorViewModel` lines 1237–1240), whereas `SaveModeAsync` checks with ordinal comparison (lines 75–80) and the SQLite unique index uses default collation. Thus a direct repository caller can save `Track` and `track` in one radar even though the UI says names are unique. This matters when interface B treats names as external handles. **Recommendation:** choose and enforce one name comparison policy at repository and database levels; never delete an unexpected blob entry as a conflict repair. Longer term, give modes a stable identifier in the canonical graph or make rename matching explicit and integrity checked.

### 6. Medium — domain validation lives almost entirely in ViewModels

`RadarModeEditorViewModel.Revalidate` lines 1224–1364 and `WaveformEditorViewModel.Revalidate` lines 479–628 enforce numerous authoring rules, but `RadarModeRepository.SaveModeAsync` checks only a nonblank name and duplicate index name, and `WaveformRepository.SaveWaveformAsync` checks only name/identity. Direct repository writes, later proxy/execute paths, imports, or migrations can persist an unsupported mode envelope, disallowed modifier, invalid Auto schedule, or non-finite numeric values. Several range checks use `<`/`>` and consequently do not reject `double.NaN`. PRISM's editor review identified similar input and preview-math gaps; CLAWE should avoid inheriting that weakness before the calculation/preview iterations. **Recommendation:** put invariant validation at a WPF-free domain boundary used by every write, and let ViewModels map those errors into field messages. Check finite values before range checks. Keep UI-specific affordance rules in the ViewModels.

### 7. Medium — one singleton EF context is a poor fit for upcoming process/reader boundaries

`App.xaml.cs` registers one `ClaweDatabaseService` singleton (line 35); that service holds one `ClaweDbContext` and hands it to all three lazy repositories (`ClaweDatabaseService.cs` lines 17–56). In the current single WPF authoring window this is workable, and it mirrors PRISM's service pattern. It becomes fragile if independent loads/saves overlap, because the same change tracker retains entities across operations and all repositories share it. More importantly, the planned proxy must open read-only while the Maintenance View alone writes, whereas this service always creates a `ReadWriteCreate` connection (`ClaweDbContext.cs` constructor). **Recommendation:** before iteration 4, make database access explicitly per operation or scoped unit of work, with separate read-only and writer factories. The process singleton/mutex and write-owner sentinel should sit at that boundary. This is future-facing architectural risk, not a claim that the current authoring screen already has a concurrent EF failure.

### 8. Low — asynchronous selection is implicit and difficult to reason about

`OnSelectedRadarChanged` sets `PendingEditorLoad = OpenRadarAsync(value)` at lines 192–205; `OnSelectedModeRowChanged` discards the `LoadSelectedModeAsync()` task at line 314. The waveform selection path uses a similar pending task. These are understandable reactions to WPF property setters that cannot be awaited, but a quick selection change can race a prior load and replace `CurrentMode` with an editor for an older selection. The radar path catches only `InvalidOperationException` in the open function, while broader loading errors can escape the discarded task. **Recommendation:** add a cancellation/version token for each selection load, publish results only when its selected key remains current, and surface exceptions consistently. Use explicit async commands where the UI allows them.

### 9. Low — the blob hash and version tag are written but not checked on read

`ClaweRadarBlobStore.UpdateBlob` writes `Sha256` and `ProtoVersion` (lines 65–70); `Deserialize` only parses protobuf bytes (lines 31–42). The tag's non-gating role is documented, so this is not a current compatibility violation. The hash currently provides no corruption detection. The parse-failure message tells an operator to delete the entire database; a damaged single radar should not require that as the only recovery advice. **Recommendation:** either validate hash/size on read and offer a targeted recovery/export path, or remove metadata that appears to promise an integrity check.

## MVVM and architecture assessment

The current boundaries follow the project's stated MVVM style. `MainWindowViewModel` is a small title property, like PRISM's shell. `RadarListViewModel` owns selected radar, editor lifecycle, footer commands, and aggregate status. `RadarModeEditorViewModel` owns mode fields, schedule, waveform browser, gating, and its child `WaveformEditorViewModel`; the latter owns one waveform's fields/modifiers and `INotifyDataErrorInfo`. XAML mostly binds to observable properties/commands. `RadarEditorView.xaml.cs` and `WaveformEditorPanel.xaml.cs` do use routed input handlers, but their purpose is WPF selection reentrancy, focus, scrolling, and a confirmation bridge. They do not themselves serialize or write domain data. That is a pragmatic MVVM exception rather than a pattern break. The dialog's click handlers are local dialog mechanics.

Two design choices should be revisited as the code grows. First, `RadarModeEditorViewModel` is about 1,375 lines and combines mode conversion, validation, waveform browsing, modifier gating, and schedule decisions. `WaveformEditorItems.cs` adds many subtype editor classes. These responsibilities are individually coherent but difficult to audit in one class; pure conversion/validation policies should move out before the calculation engine and interface-B rollups increase coupling. Second, the mode Save round-trips `_loadedWaveforms` wholesale (`BuildProto` lines 1058–1062), then a separate waveform Save writes the same radar blob again. The recent clobber regression and its `RefreshWaveformsAsync` fix (lines 395–419) show that this arrangement is inherently state-sensitive. A single aggregate Save would make the current loaded-graph synchronization less delicate.

The project boundaries are better than coupling CLAWE to PRISM as a plugin. The copied PRISM theme tokens and editor composition fit the stated standalone deployment. The legacy suite is chiefly a behavior/field reference; the new app's data-authoring and STS integration are different responsibilities, so a one-to-one legacy ViewModel port would be misleading. The deck's proxy with 0..1 Maintenance and 0..n Execution views, and interface B's RabbitMQ/protobuf messages, are not implemented yet. They are scheduled for later iterations and should be assessed as design readiness, especially for the database access pattern above.

## ViewModel walkthrough

### `MainWindowViewModel.cs` and shell

The main-window ViewModel only generates `ApplicationTitle`. `App.xaml.cs` is the composition root: it builds the host, registers pages and ViewModels, starts the host, initializes SQLite, applies the dark theme, and shows `MainWindow`. `MainWindow.xaml.cs` creates Maintenance, Operate placeholder, and Viz Spike navigation entries and checks unsaved radar edits on close. This matches PRISM's small shell-VM convention. When process roles arrive, startup mode/instance enforcement belongs in this composition layer, while visible role-specific state can enter a shell ViewModel.

### `RadarListViewModel.cs` — page and aggregate editor lifecycle

Read it in five passes. (1) Lines 38–159 define the radar/mode selection, identity fields, editing and dirty indicators, footer status, and breadcrumb. (2) Lines 192–324 react to selection and child property changes; this is where editor state is coordinated and the dirty-state finding originates. (3) Lines 331–450 load radar/mode index rows and construct the current mode editor. (4) Lines 458–573 handle opening, new drafts, discard, and exit. (5) Lines 576–773 save/delete radar and add/delete modes. The class is the application controller for one authoring session, which is a reasonable ViewModel role; the atomicity of its Save is the central correction.

### `RadarModeEditorViewModel.cs` — mode form plus waveform orchestration

Its `InitializeAsync` (lines 722–758) loads an existing proto mode or seeds a new one. `LoadFrom` (starting line 836) maps protobuf choices into editable fields and retains loaded waveforms. `BuildProto` (lines 972–1064) performs the reverse mapping, including operating mode, constraints, modifiers, schedule, and preserved waveforms. `Revalidate` (lines 1224–1364) checks field and schedule rules and updates tab error indicators. The waveform section (lines 395–617) refreshes summary/index rows, opens or adds a child editor, and writes the open child only after the mode Save. `RecomputeWaveformUsage` and modifier gating keep a mode from disabling features a waveform uses. This is the most complex file: follow the data flow `Initialize → edit/validate → BuildProto → parent Save → RefreshWaveforms` before studying each field property.

### `WaveformEditorViewModel.cs` and modifier items

`InitializeNew` and `LoadFrom` (lines 190–274) seed or decode one waveform. `ApplyModifierGating` (lines 285–364) applies the current mode's allowed base/modifier set. `BuildProto` (lines 389–445) maps the editable state to `ClaweWaveformInstance`, with PD-only and SP-only branches; the separate modifier item classes each round-trip one modifier subtype. `Revalidate` (lines 479–628) applies name, compatibility, and deck range checks. The editor has no persistence dependency, which is good: it emits a graph for its parent to save. A useful reading exercise is a PD waveform with Base Agile PRI and LFM: trace XAML selection → modifier item → `Revalidate` → `BuildProto` → `RadarModeEditorViewModel.SaveCurrentWaveformAsync` → `WaveformRepository.SaveWaveformAsync`.

## Test and evidence limits

The suite has valuable successful-path coverage: repository CRUD and relaunch persistence, blob/index sync, mode rename and waveform preservation, editor validation, footer behavior, schedule references, and a 2,000-waveform save benchmark. It does not establish failure atomicity, mode-switch handling of radar-only edits, two rapid competing selection loads, read-only process enforcement, or repository-level validation. Those are the focused tests most likely to change the verdict.

I attempted `dotnet test CLAWE_UI.slnx --no-restore --verbosity quiet` from the solution root. It remained silent for several minutes and did not finish during this review, so I interrupted it. This report therefore rests on static inspection and the existing test source, not a fresh passing run. I did not launch the WPF UI or exercise a click-through in this environment. The working tree was clean before the review; this report is the only new file.
